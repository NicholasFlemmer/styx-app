Project · Agent · Repo switcher

A local desktop app (macOS + Windows) that embeds an editor, switches between projects in one window, supervises coding-agent sessions, and gates agent access to deploy and server targets.

1. Problem framing

Developers running several agents across several repos today juggle: one IDE window per repo, one terminal tab per agent, and credentials scattered across shell env, .env files and CLI logins. Three failure modes recur:

  • Lost attention. An agent in another window is blocked on a question for twenty minutes and nobody notices.
  • Collisions. Two agents edit the same working tree; one clobbers the other's changes.
  • Credential sprawl. Agents get prod keys by copy-paste, with no scope, expiry or record.

The app's job is to make where am I, who's working, what can they touch answerable at a glance, from one window.

2. Personas (from your brief)

Solo dev, many side projects
Wants fast switching and zero setup. Cares about the switcher (1a/1b) and palette. Tolerates fewer guardrails.
Team lead, client repos
Needs isolation between clients (separate targets, separate keys) and per-project settings that travel with the repo (1m).
Platform / infra engineer
Owns the targets. Wants policies, MFA on prod write, audit log, exportable config (1f).
Non-technical founder
Supervises rather than codes. Needs the attention-ordered board (1c) with plain-language approve/deny; rarely opens the editor.

Tension: persona 1 wants fewer prompts; persona 3 wants more control. Policies (auto-approve tiers) are how one product serves both.

3. Analogues and what to borrow

  • Notion — persistent sidebar with a workspace switcher at the top; everything hangs off one tree. Borrow: the rail + tree in 1a, and "recent" lists. Avoid: nesting depth.
  • VS Code — User vs Workspace settings, Quick Open, multi-root workspaces, integrated terminal. Borrow: the settings split (1m), palette conventions, and status bar as a place for lock state (1h). Its weakness is one-window-per-repo; that is the gap this app fills.
  • Composio-style auth brokers — a catalogue of connections with OAuth, scoped tokens issued to agents rather than raw keys. Borrow: connect flow, scope model, per-agent tokens (1e).
  • tmux / Warp / Zellij — tiled live sessions, focus-zoom, keyboard pane switching (1d).
  • Linear / Raycast — verb-first palette with grouped results and inline metadata (1k); flat searchable settings (1n).
  • macOS TCC / 1Password prompts — an approval prompt that states who is asking, for what, and offers "once / for 1 hour / always". Users already trust this vocabulary.

4. Object model

Every screen composes six objects. Naming them consistently in UI copy matters more than any layout choice.

Project — folder + metadata; has 1 Repo, N Worktrees, N Targets
Repo — remote(s), default branch
Worktree — checkout of one branch; owned by you or one Agent
Agent session — CLI process (claude, codex, gemini, cursor, shell) bound to a Worktree; state: idle | working | needs-you | done
Target — Vercel / AWS / GCP / Supabase / GitHub connection, tagged env: prod | staging | preview
Grant — (Agent session, Target, scope, expiry) — the unit the auth gate issues, shows, and revokes

Rule that falls out of this: one agent = one worktree by default. It removes the collision problem without asking users to understand git internals.

5. Design principles

  1. Attention is the scarce resource. Sort by "needs you" first everywhere: rail badges, board columns, palette results, dock/tray icon.
  2. State travels with the object. A project tile, an agent card and a palette row all show the same three glyphs: agent dot, branch, lock. Users learn one vocabulary.
  3. Grants decay. Default duration is time-boxed; "always" is opt-in and visibly different. Expiry is shown as a countdown, not a timestamp.
  4. Ask in context, manage centrally. The prompt appears where the agent asked (1e, 1d); the record and the policies live in one inbox (1f).
  5. Keyboard parity. Every switch, focus and approve action has a shortcut, and the palette can do all of it.
  6. Never write secrets to disk in the repo. OS keychain only; project config files reference targets by name.

6. Screen-by-screen notes

Switcher / home. 1a suits founders and team leads (awareness without action). 1b suits solo devs who live in the editor. Recommendation: ship the rail from 1a as collapsible; the overlay from 1b is the palette's Projects scope, so both exist at little extra cost.

Agent board. 1c and 1d are two views of the same sessions. Board for triage, tiles for work; a toggle in the header. Cards and pane headers must render the same status text. Sessions past ~6 need a stacked/list mode.

Auth gate. The request sheet in 1e is the core interaction. It must show: agent, target, environment tag, the agent's stated reason (verbatim), scope checkboxes, and duration chips. Deny needs no reason. Prompt fatigue is the known failure: 1f's policies (auto-approve reads on staging; always ask + MFA on prod write) are the mitigation and should ship in v1, even if minimal.

Repo view. 1g makes the worktree model visible; 1h hides it behind familiar tabs. Suggest 1h as the default editor surface and 1g as the "Repo" page for review and cleanup.

Onboarding. 1i gets the home screen populated on first launch (scan for repos, import VS Code recents); 1j defers agents and targets to first use. Recommendation: step 1 of the wizard only, then just-in-time for the rest.

Palette. 1k is the better end state; 1l is cheaper and is a valid v1. Either way, lock state must appear on every row that could be blocked by a grant.

Settings. 1m matches the VS Code mental model and supports a committed project config file; 1n is faster to scan. Recommend 1m with search from 1n.

6b. Main workspace and the embedded editor

Turn 2 of the wireframes adds the screen you spend the day in. 2a mirrors the VS Code + Claude Code extension layout: files left, editor centre with the agent's pending hunks inline, terminal below, and an agent chat panel on the right (message bubbles, plan, diff links, inline yes/no, a prompt box with @file and /commands; tabs per session). 2b inverts it: conversations centre, all sessions listed left like a messaging app, code as a diff drawer. Recommendation: 2a default, 2b as a mode for supervisors.

How to get the editor. Three routes, easiest first:

  1. Launch the user's IDE. The app is switcher, agent board and gate; "Open editor" launches VS Code or Cursor on the right worktree. Days of work, full extension support, but two windows and no inline diffs. Fallback, not the brief.
  2. Embed an editor component. Monaco (VS Code's editor widget, MIT) or CodeMirror inside an Electron/Tauri shell. Syntax highlighting, diffs, multi-file tabs in weeks. No VS Code extension ecosystem, debugger or language servers unless LSP is wired by hand. Enough for reviewing agent diffs and light edits; not a full daily IDE.
  3. Ship a VS Code-based IDE. Build on the open-source Code-OSS core (as Cursor and Windsurf do) or run OpenVSCode/code-server in a webview. Full editor with extensions, but you own a large codebase, upstream merges, and marketplace constraints (Microsoft's marketplace is closed to forks; Open VSX is the alternative). Months and a dedicated team.

Building an editor from scratch is not realistic. Recommendation: route 2 for v1, with route 1 as an "open in VS Code" escape hatch on every file and worktree. 2a holds either way: the editor pane is Monaco, the chat panel and gate are yours, and route 3 becomes a later upgrade without a redesign.

7. macOS + Windows considerations

  • Title bar. Traffic lights left on macOS; caption buttons right on Windows. Keep the project switcher control in the title bar centre so it works on both.
  • Shortcuts. ⌘ ↔ Ctrl mapping throughout; show the platform's glyphs. Avoid Ctrl+Alt combos that collide with Windows AltGr layouts.
  • Secrets. macOS Keychain and Windows Credential Manager; MFA via system prompt (Touch ID / Windows Hello) for prod-write grants.
  • Background presence. Dock badge on macOS, tray icon + toast on Windows for "agent needs you". Both need a do-not-disturb toggle.
  • Shells. Agent CLIs run in the user's default shell; on Windows offer PowerShell / WSL selection per project, since some agents behave differently under each.
  • Paths and line endings. Worktree creation must handle long paths and CRLF settings per repo; surface these once in project settings, not in every flow.

8. Security notes for the gate

  • Issue per-session, scoped tokens to agents where the provider supports it (Vercel, GitHub, Supabase, GCP short-lived creds, AWS STS). Fall back to injecting env vars into the agent process only for the grant's lifetime.
  • Every grant, use, and revocation is logged with agent, worktree, and the command that triggered it. The audit log is a first-class screen, not a settings sub-page.
  • Revocation is one click from any surface that shows a lock glyph.
  • Environment tags (prod / staging / preview) are set at connect time and drive policy; make the prod tag visually loud everywhere.

9. Open questions

  1. Editor route (see 6b): confirm Monaco for v1, and whether LSP for the top 3 languages is in scope.
  2. Are agent sessions per-project only, or can one agent span repos (e.g. a monorepo plus an infra repo)?
  3. Should team policies sync via the repo, a cloud account, or stay per-machine in v1?
  4. How do agents request access: a local broker the CLIs call, or the app intercepting failed auth in the agent's output?
  5. Windows: is WSL a hard requirement for target audiences, or a nice-to-have?

10. Suggested next step

Pick one composite: rail from 1a + editor surface 1h + board/tiles toggle (1c/1d) + grant sheet 1e backed by policies from 1f. Then wireframe the single most important flow end to end: an agent asks for prod → you grant for 1h → it deploys → the grant expires.
